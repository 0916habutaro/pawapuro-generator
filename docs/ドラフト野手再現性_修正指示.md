# ドラフト候補用の野手の再現性 修正指示

## 目的

ドラフト候補用の野手は、**同じseedでも、Pythonを起動するたびに能力が変わることがある**。「同じseedなら同じ選手」が崩れているので直す。

検証では `PYTHONHASHSEED=0` に固定してしのいでいるが、アプリ（Streamlit）を起動するたびに文字列のハッシュの値が変わるので、使う人から見ると同じseedで別の選手が出る。

**前提**: PR #110 をマージした後の main（b602575）で作業する。

---

## 0. 調査の結果

### 0-1. 再現
`PYTHONHASHSEED` を 0・1・2 に変えて、6区分（架空球団用・ドラフト候補用・助っ人外国人用 × 投手・野手）を seed 1〜300 で作り、0 の結果と比べた。

| 区分 | 0 と 1 の違い | 0 と 2 の違い |
|---|---|---|
| ドラフト候補用・野手 | 134人／300 | 136人／300 |
| ほかの5区分 | 0人 | 0人 |

- 変わる項目は主に能力（ミート・守備力・捕球）。能力が変わると、その後の特能・名前・出身地・誕生日・用具なども変わる選手がいる。
- 乱数を引く回数と順番は、ハッシュの値によらず同じだった。変わるのは、**引いた乱数をどの能力に当てるか**。

### 0-2. 原因
`app.py` 1386行目の定数が**集合（set）**になっている。

```python
TECHNICAL_FIELDER_KEYS = {"ミート", "守備力", "捕球"}
```

集合の並び順は、文字列のハッシュで決まるので、起動ごとに変わる。`apply_fielder_development_mods`（3237行目付近）は、この順番で乱数を引いて各能力に足し引きしている。

```python
if development_stage == "素材型":
    ...
    for key in TECHNICAL_FIELDER_KEYS:
        values[key] -= rng.randint(3, 7)
elif development_stage == "即戦力型":
    for key in TECHNICAL_FIELDER_KEYS:
        values[key] += rng.randint(3, 6)
```

- `development_stage`（素材型・即戦力型）はドラフト候補用にしか付かない（`choose_development_stage`）。だからドラフト候補用の野手だけが変わる。
- 同じ定数を使うほかの2か所（3161行目付近・3265行目付近）は、どの能力からも同じ3を引くだけなので、順番に関係なく結果は同じ。
- `PHYSICAL_FIELDER_KEYS`（1387行目）も集合だが、今は繰り返しに使われていない。

### 0-3. 試した修正
集合を、**`PYTHONHASHSEED=0` のときの並び順**と同じ並びのタプルに変えた。

```python
TECHNICAL_FIELDER_KEYS = ("捕球", "ミート", "守備力")
```

| PYTHONHASHSEED | 修正前の0の結果と違う選手（6区分×300人） |
|---|---|
| 0 | 0人 |
| 1 | 0人 |
| 2 | 0人 |

- この並び順にすると、**`PYTHONHASHSEED=0` で作った今の結果と完全に同じ**になる。検証のスナップショット（`data/config/check_snapshot.csv`）や基準値ファイルは、どれも `PYTHONHASHSEED=0` で作ったので、更新しなくてよい。
- `PYTHONHASHSEED=0` のときの並び順は `python -c "print(list({'ミート', '守備力', '捕球'}))"` を `PYTHONHASHSEED=0` で実行して確かめられる（`['捕球', 'ミート', '守備力']`）。

## 1. 修正の内容

### 1-1. 原因の修正
- `TECHNICAL_FIELDER_KEYS` を `("捕球", "ミート", "守備力")` のタプルにする。並び順を変えない理由（`PYTHONHASHSEED=0` の結果と同じにするため）をコメントに書く。
- `PHYSICAL_FIELDER_KEYS` も、`PYTHONHASHSEED=0` のときの並び順（`("パワー", "走力", "肩力")`）のタプルにする。今は繰り返しに使われていないが、今後同じ不具合を作らないため。
- `key in TECHNICAL_FIELDER_KEYS` のような「含まれるか」の判定はタプルでもそのまま動く。集合として使っている箇所（`|` や `&` など）があれば、その箇所だけ `set(...)` で包む。

### 1-2. ほかに同じ危険がないかの点検
次をすべて点検し、一覧にして報告する。
- `app.py`、`generator/` の全ファイルで、**集合（set・frozenset）を順番に回している箇所**（`for ... in 集合`、内包表記、`list(集合)`、`sorted` のない `rng.choice(list(集合))` など）。
- 集合から作った辞書や一覧を、乱数と組み合わせて使っている箇所。
- 文字列の `hash()` を使っている箇所。

各箇所を次のどれかに分ける。
| 分類 | 対応 |
|---|---|
| 乱数・丸め・上限などで、順番によって結果が変わる | 1-1 と同じく、`PYTHONHASHSEED=0` のときの並び順のタプル（または `sorted`）にする。結果が変わらないことを 2-1 で確かめる |
| 順番によらず結果が同じ（全部に同じ値を足すだけ、など） | 直さなくてよい。一覧に「順番に関係なし」と書く |
| 判断がつかない | 直さずに、一覧に書いて相談する |

### 1-3. 検証スクリプトの扱い
- `run_checks.py` の `PYTHONHASHSEED=0` の固定は**残す**（念のための二重の守り）。コメントの「ドラフト候補用の野手の不具合を直すまでの措置」は、「ハッシュの値によらないことは `tests/test_hash_independence.py` で確かめている。念のため固定している」に書き換える。
- README・AGENTS.md・各スクリプトにある、この不具合についての注意書きを探して、直したことが分かるように書き換える。

## 2. 検証

### 2-1. ハッシュの値によらないこと（新しいテスト `tests/test_hash_independence.py`）
- `subprocess` で、`PYTHONHASHSEED` を 0・1・2・12345 の4通りにして Python を起動し、同じ選手を作らせて、結果が完全に一致することを確かめる。
  - 個別生成: 6区分 × seed 1〜200
  - 球団生成: seed 1〜3 の3球団
- 比べるのは、`generate_player` の結果全体（`id`・作成日時など毎回変わる項目を除く）。
- 時間がかかりすぎる場合は人数を減らしてよい（ただしドラフト候補用・野手は200人を下回らない）。

### 2-2. 今の結果と変わらないこと
- `PYTHONHASHSEED=0` で、6区分 × seed 1〜1000 と球団生成 seed 1〜50 が、修正前と完全に一致する。
- `run_checks.py` を正式な規模で流し、「悪化」0件、不合格0件。スナップショットは更新しない（変わらないはずなので、更新が必要になったら原因を調べて報告する）。
- 全テストが通る。
