# 判定の整理 改修指示（検証スクリプトの合否の作り直し）

## 目的

ここ数回の改修で、検証スクリプトの「受け入れ済みの不合格」が増えた。毎回「これは抽選のばらつき」「これは前から」と人が判断していて、**本当に悪くなった項目が混ざっても気づけない**状態になっている。

今回は**生成ロジックを一切変えずに**、検証の仕組みを次のように作り直す。
1. 判定を種類ごとに分け、それぞれに合った合否の付け方にする。
2. 抽選のばらつきを数字で見積もり、「境界ぎりぎり」を不合格と区別する。
3. 受け入れた不合格を記録し、それより悪くなったときだけ不合格にする。
4. 「改修前から変わっていない」の基準値を1か所にまとめ、更新の手順を決める。
5. 全部の検証を同じ条件で1回で流せるようにし、結果を1枚にまとめる。

**前提**: PR #109 をマージした後の main（e6e067c）で作業する。

### 0-3. 問題点
- **正式な規模で流していない**。`validate_team_mode.py` の既定は500球団なのに、時間を減らすために200球団で流した結果で合否を話している。背番号の2項目は、500球団なら合格する。
- **抽選のばらつきの大きさが分からない**。0.2だけ外れたのが誤差なのか本当のずれなのか、毎回の判断になっている。
- **実在側の誤差を見ていない**。実在は36チームしかないので、実在の90%点そのものに誤差がある。
- **判定の種類が混ざっている**。「実在に合わせる判定」「改修前から変わっていないことを確かめる判定」「設計上の条件（戦力レベルの (d)(e)(f) など）」が同じ ✅／❌ で並んでいる。
- **改修前の基準値がスクリプトにばらばらに書かれている**（`check_age_profile.py` の `BASELINES`、`check_pitcher_control.py` の先発のスタミナ 58.75／58.70、`check_fictional_balance.py` の改修前の値など）。更新の手順も毎回違う。
- **同じseedでも結果が変わる**。ドラフト候補用の野手は `PYTHONHASHSEED` で結果が変わる（不具合。今回は直さない）。

## 1. 判定の種類

すべての判定に、次のどれかの種類を付ける。

| 種類 | 意味 | 合否の付け方 |
|---|---|---|
| **実在** | 実在データに合わせる判定 | 2章の誤差を考えて「合格／要注意／不合格」 |
| **固定** | 改修前から変わっていないことを確かめる判定 | 4章の基準値ファイルと比べる。意図して変えたときは、理由を付けて基準値を更新する |
| **設計** | 実在とは別に決めた条件（戦力レベルの (a)〜(f)、チームカラーの目安、背番号の重複なしなど） | 今の基準のまま「合格／不合格」 |
| **参考** | 合否を付けない表示 | 表示だけ |

## 2. 抽選のばらつきの見積もり（「実在」の判定）

### 2-1. 生成側の誤差
- 判定する値ごとに、生成のばらつき（標準誤差）を見積もる。
  - 球団単位の値（球団ごとの平均の10%・90%・標準偏差など）: 球団を単位にブートストラップする（例: 200回）。
  - 選手単位の値（平均・割合・相関など）: 選手を単位にブートストラップするか、seed を10のまとまりに分けて、まとまりごとの値のばらつきから求める。どちらでもよいが、スクリプト間で同じやり方にする。
- 重い場合は、ブートストラップの回数を減らすか、まとまりで分ける方式にしてよい。かかった時間を報告する。

### 2-2. 実在側の誤差
- 実在が球団単位の値（36チームの10%・90%・標準偏差）のときは、実在の36チームでも同じようにブートストラップし、実在側の誤差も出す。
- 選手単位の値（実在1,126人の平均など）も同じ。実在の人数が少ない区分（例: 救援・左の137人）ほど誤差が大きくなる。

### 2-3. 合否
- 誤差を合わせたもの: `誤差 = √(生成の標準誤差² + 実在の標準誤差²)`。範囲の基準を実在から決めていない項目は、生成側だけ。
- **合格**: 値が範囲の内側。
- **要注意**: 値が範囲の外側だが、境界からの距離が `2 × 誤差` 以内。
- **不合格**: 境界からの距離が `2 × 誤差` を超える。
- 範囲そのものは今の値から変えない。誤差の分を「要注意」で吸収する。
- 表には「値、範囲、誤差、境界からの距離（誤差の何倍か）、合否」を並べる。

## 3. 受け入れ済みの不合格

### 3-1. 記録ファイル
- `data/config/accepted_deviations.json` を作る。1項目ごとに次を持つ。
  ```json
  {
    "id": "validate_team_mode.spread.投手の査定の平均.p90",
    "accepted_value": 303.1,
    "limit": 301.45,
    "direction": "upper",
    "reason": "実在36チームの分布の端で誤差が大きい。救援のコントロールを優先した",
    "pr": "#108, #109",
    "date": "2026-10-04"
  }
  ```
- `id` は判定ごとに決まった名前（4-2）。

### 3-2. 合否
- 記録された項目は、値が `accepted_value` より悪くなっていなければ **「受け入れ済み」**。
- `accepted_value` から誤差の2倍を超えて悪くなったら **不合格**（「受け入れた値より悪化」と表示）。
- 合格の範囲に戻ったら「合格」と表示し、記録ファイルから外すよう促す表示を出す。

### 3-3. 初期の中身
0-2 の4項目を、**正式な規模で流し直したうえで**判定する。
- 2章の誤差で「合格」か「要注意」になった項目は、記録しない。
- それでも「不合格」になった項目だけを、今の値で記録する。
- どれをどう扱ったかを完了報告に書く。

## 4. 「固定」の基準値

### 4-1. 基準値ファイル
- `data/config/check_baselines.json` に、スクリプトに書かれている「改修前の値」をすべて移す。
  - `check_age_profile.py` の `BASELINES`（球団・投手の特能の数 4.27、査定 291.9 など）
  - `check_pitcher_control.py` の先発のスタミナ（58.75／58.70）
  - `check_fictional_balance.py` の改修前のコントロール・スタミナの値
  - そのほか、スクリプトを全部見て見つけたもの
- 1項目ごとに、値・幅（±いくつ）・最後に更新したPR・理由を持つ。

### 4-2. 判定ごとの名前（id）
- すべての判定に、変わらない名前を付ける（例: `check_pitcher_control.relief.stamina.sd`）。基準値ファイルと受け入れ記録は、この名前で項目を指す。
- 判定の表示名を変えても、id は変えない。

### 4-3. 更新の手順
- 各スクリプトに `--update-baselines --reason "理由"` を付ける。
  - 「固定」の判定の今の値を基準値ファイルに書き込む。
  - `reason` が空なら書き込まない。
- 書き込んだ項目と、前の値・新しい値を表示する。

## 5. まとめて流す仕組み

### 5-1. `scripts/run_checks.py`（新規）
- 0-1 の全スクリプトを、正式な規模で順に流す。
  - 個別生成の CSV が必要なスクリプト（`check_fictional_balance.py` など）には、既存のサンプル生成スクリプトで作った CSV を渡す。
- `PYTHONHASHSEED=0` を固定して流す（ドラフト候補用の野手の不具合を直すまでの措置）。
- `--quick` を付けると規模を小さくして流す。
  - その結果は**すべての合否を「参考」として表示**し、見出しに「簡易版（合否には使わない）」と出す。
- `--only validate_team_mode,check_pitcher_control` のように一部だけ流せるようにする。
- それぞれのスクリプトの所要時間を記録する。

### 5-2. まとめのレポート `reports/checks/summary.md`
- 先頭に、合格・要注意・受け入れ済み・不合格の件数。
- その下に、合格以外の項目の一覧（id、値、範囲、誤差、種類、理由）。
- 各スクリプトの詳細レポートへのリンク。
- 実行した main のコミット、規模、`--quick` かどうか、所要時間。
- 終了コード: 不合格が1件でもあれば1。要注意と受け入れ済みは0。

### 5-3. 各スクリプトの共通化
- 合否の付け方（1〜4章）を共通の小さなモジュール（例: `scripts/checklib.py`）にまとめ、各スクリプトから使う。
- 各スクリプトは、判定の一覧を同じ形の CSV（`reports/checks/<スクリプト名>.csv`）にも出す。列は id、種類、表示名、値、範囲、誤差、合否、理由。
- 今の表示（`summary.md` など）は残してよい。共通の CSV を追加する形でよい。

## 6. 検証

### 6-1. 今の main での結果
- `run_checks.py` を正式な規模で流し、不合格が0件になることを確認する（受け入れ済み・要注意はあってよい）。
- 0-2 の4項目がそれぞれどうなったか（合格、要注意、受け入れ済み）を表にする。

### 6-2. 悪くなったときに気づけるか（検出力のテスト）
- わざと生成を悪くした状態で流し、**不合格になる**ことを確認する。少なくとも次の3つ。
  1. 救援のコントロールを+3する。
  2. 戦力レベルの倍率を強くして、球団ごとの散らばりを今の1.3倍程度にする。
  3. 背番号の42番の外国人の倍率を極端にする。
- 悪くする処理はテストやスクリプトの中だけで行い、本体のコードには残さない（`monkeypatch` など）。
- 規模を小さくして流すテストにしてよい（`tests/test_check_sensitivity.py`）。その場合でも、「要注意」ではなく「不合格」になる程度に大きく悪くする。

### 6-3. 変わらないこと
- 生成の結果は seed まで改修前と同じ。生成のコード（`app.py`、`generator/`）は変更しない。
- 既存のテストがすべて通る。
- 各スクリプトを単体で流したときの今の使い方（引数）は残す。

## 8. 今回やらないこと
- 生成ロジックの変更（どんなに小さくても）。
- 判定の範囲そのものの変更。誤差の考え方を入れる以外で範囲を変えたい項目があれば、変更せずに一覧にして報告する。
- ドラフト候補用の野手の `PYTHONHASHSEED` の不具合の修正（別の改修）。
- CI の設定（GitHub Actions など）。
