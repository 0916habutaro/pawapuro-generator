# パワプロ風 架空選手生成

## 概要

パワプロ風 架空選手生成は、Python + Streamlit + SQLiteで動作する個人利用専用のローカル用ツールです。外部公開・配布を前提としません。パワプロのペナント向けに、実在選手ではなく架空選手をランダム生成することを目的としています。

主な設計方針は次のとおりです。

- 投手・野手を選択して生成できます。
- カテゴリは「架空球団用」「ドラフト候補用」「助っ人外国人用」から選択できます。
- ユーザーが細かな能力値を指定せず、年齢・国籍・名前・能力・特殊能力などを内部ロジックで自動生成します。
- 生成結果をローカルSQLiteへ保存できます。
- 保存済み選手の履歴とバランスを確認できます。
- 画面からCSV・Excelへ出力できます。
- 基本機能はインターネット接続なしで利用できます。

このツールは実在選手を完全再現するものではありません。ペナント用の架空選手データを手軽に作るためのローカルアプリです。

## 主な機能

- 投手・野手の架空選手生成
- 3カテゴリ別の生成
- 国籍・地域別の名前生成
- パワプロ風の能力カード表示
- 数値能力とA〜Gランク表示
- 投手の球速、コントロール、スタミナ、変化球、第二球種、ストレート系第二種
- 野手の弾道、ミート、パワー、走力、肩力、守備力、捕球、サブポジション
- 特殊能力とランク系特殊能力
- 1球団分（支配下ロスター）をまとめて作る「球団生成」
- SQLiteへの保存
- 過去生成選手の履歴表示
- バランス確認画面での集計
- CSV・Excel出力
- 検証スクリプトによる生成結果レビュー

## 動作環境

- 主対象OS: Windows 10 / 11
- Python: 3.11で動作確認済み
  - このリポジトリの最終確認はPython 3.11.8で実施しています。
  - 未確認のPythonバージョンでの動作は断定しません。
- 必要な空き容量: 最低200MB程度
  - 大量生成、SQLite履歴、検証レポートを多く残す場合は1GB以上の余裕を推奨します。
- ブラウザ: Microsoft Edge、Google Chromeなどの一般的なモダンブラウザ
- SQLite: Python標準ライブラリの`sqlite3`を利用します。別途SQLiteをインストールする必要はありません。
- Microsoft Excel: Excelファイルを閲覧する場合のみ必要です。出力自体はPythonパッケージ`openpyxl`で行います。

## 基本的な使い方

1. サイドバーの「表示する画面」で「選手生成」を開きます。
2. 「投手 / 野手」で「投手」または「野手」を選びます。
3. 「カテゴリ」で「架空球団用」「ドラフト候補用」「助っ人外国人用」のいずれかを選びます。
4. 「生成人数」を指定します。
5. 「生成する」ボタンを押します。
6. 生成結果の能力カードを確認します。
7. 生成された選手はSQLiteへ自動保存されます。

9. 必要に応じて「CSV出力」「Excel出力」を使います。
10. サイドバーの「表示する画面」で「バランス確認」を開き、保存済み選手の分布を確認します。

## 選手カテゴリ

### 架空球団用

- 実在12球団の能力分布を主な参考にした標準カテゴリです。
- 弱い選手から主力級まで幅広く生成します。
- 年齢・タイプ・ポジションに応じた能力差があります。
- 日本人投手の球速は、実在（2024〜2026年版）と同じく左投手のほうが約3km/h遅く、救援のほうが先発より速くなります（平均の目安: 先発 右151・左149、救援 右153・左150）。
- 日本人投手のコントロールは、実在（2024〜2026年版）と同じく先発は左投手、救援は右投手のほうが少し高く、救援は先発より約6〜10低くなります。救援は幅も実在に合わせて縮めています（球団生成での平均の目安: 先発 右54・左57、救援 右49・左47。個別生成は二軍級が多いので、どれも1〜2低めです）。先発のスタミナは実在に合わせて、左が約2低く、幅が広くなります（先発のスタミナの目安: 右 平均57・左 55、標準偏差 約11。21歳以下は若手の補正で合わせているので対象外）。
- 日本人の救援投手のスタミナは、実在（2024〜2026年版）と同じく先発より散らばりが小さく、コントロールの良し悪しとの結びつきも弱くなります（救援のコントロール×スタミナの相関の目安 0.2、先発は 0.5。救援のスタミナの平均の目安 47、標準偏差 6。21歳以下は若手の補正で合わせているので対象外）。
- 日本人投手の変化球の総変化量（ストレート系第二球種を除く）は、実在と同じく、コントロール・スタミナの良い投手ほど多くなります（先発の総変化量×コントロールの相関の目安 0.5、救援 0.3。球団内で査定が下位の投手は平均5.3、上位は7.4）。変化球の種類・数・方向は変えません。19歳以下は変化量の上限で決まるので対象外です。

### ドラフト候補用

- 架空球団用より全体的に未完成な選手を生成します。
- 若手中心です。
- 特殊能力や完成度は控えめです。
- 低確率で即戦力・上位候補も生成されます。

### 助っ人外国人用

- 外国籍中心です。
- 能力や特殊能力が尖りやすいカテゴリです。
- 当たり選手だけでなく外れ選手も生成されます。
- 架空球団用より特殊能力数が多い傾向があります。

## 球団生成

上部ナビゲーションの「球団生成」で、実在NPB球団に近い人数構成の1球団分（支配下ロスター、63〜70人）をまとめて作ります。ペナント開始時に1球団を作る用途向けです。

### 使い方

1. 左のサイドバーで、球団名（任意）と球団seed（任意）を入力します。
   - 球団名が空欄なら「架空球団{番号}」になります（番号は次に保存する球団のID）。
   - 球団seedが空欄ならランダムです。同じseedなら、構成・選手・名前・能力・背番号まで同じ球団になります。
2. 「球団を生成」を押します（1球団あたり数秒かかります）。
3. 概要・構成チェック表・投手一覧・野手一覧を確認します。表の行を選ぶと、その選手の能力カードが表の下に出ます。
4. 気に入ったら「この球団を保存」を押します。**生成しただけでは保存されません**。作り直した球団はDBに残りません。

### 人数構成は実在データが基準

`data/reference/real_team_composition_2022_2026.csv`（2022〜2026年版パワプロ、12球団×5年＝60チーム）から1チームを「構成テンプレート」として選び、少しだけ揺らしてから、その人数に合わせて選手を作ります。

- 投手数・野手数、ポジション別の野手数、先発・救援の人数、左投手数、外国人の投手数・野手数
- 年齢帯ごとの人数（2026年版の割合に合わせ、先に作った外国人の分を引いて国内選手を作る）
- 国内選手の選手格（スター級・一軍主力級など）の人数を、投手・野手それぞれ球団ごとに決めます。期待値は戦力レベル・チームカラーの倍率と年齢帯の人数から計算し、端数は球団seedの乱数で配ります。型の人数（野手全員の型、先発の型＝ポジションスタイル）も同じように決めます。1人ずつ独立に抽選すると、同じ戦力レベルでも選手格の人数が球団ごとに大きくぶれるためです。
- 外国人は「助っ人外国人用」、国内の選手は「架空球団用」の生成処理をそのまま使い、条件（ポジション・役割・左右・年齢帯・選手格・型の残り人数）に合う選手が出るまで作り直します（棄却サンプリング）。どうしても出ないときは、型 → 選手格 → 左右 → 年齢帯 → 役割・ポジションの順に条件をゆるめ、その人数を警告として表示します。

### 戦力レベルとチームカラーはランダム

- 戦力レベル（強豪・中位・弱小）と、球団ごとの戦力指数（同じ強豪でも強さに幅がある）。投手と野手の戦力指数は同じ値です。「投手は強いが打線が弱い」球団は、選手の顔ぶれの違いやチームカラー（投手王国・強力打線など）で生まれます。
- 戦力レベル・チームカラーの効き方は、球団ごとの査定・能力の平均の散らばりが実在（2024〜2026年版の36チーム）と同じくらいになるように合わせています（`scripts/validate_team_mode.py` の「球団ごとの散らばり」）。
- チームカラー（特色なし・投手王国・強力打線・機動力・守備重視・若手育成・ベテラン重視）と効き具合。25%の球団は2つ目のカラー（サブカラー）を持ちます。
- どちらも国内の選手の「選手格」「型」「年齢」の出やすさを変えるだけで、能力の作り方そのものは個別の選手生成と同じです。外国人には効きません。
- 倍率の基準値・範囲・揺らぎ幅は `generator/team.py` の定数にまとめてあります。
- 戦力指数・効き具合・最終的な倍率は、画面の「球団の内部パラメータ」で確認できます。

### 背番号

球団生成でだけ、全員に背番号（0〜99と00）を付けます。`data/reference/real_uniform_numbers_2022_2026.csv` の番号ごとの使われ方（投手・捕手・内野手・外野手・外国人）と、球団内の査定の順位・年齢をもとに割り当てます。欠番（永久欠番など）も球団ごとに0〜6個決まり、その番号は誰も使いません。

- 外国人は、実在で外国人が使った番号（42・99・90番台など）に付きやすく、実在で外国人がいない番号（1・17・18・19番など）にはほとんど付きません。
- 若手ほど大きい番号（31〜69番）、ベテランほど小さい番号（0〜30番）に付きやすくなります（年齢に対して連続に変わる倍率）。
- 背番号は文字列で保存します（"0" と "00" は別の番号）。並びは 0 → 00 → 1 → … → 99。
- 個別の選手生成では背番号を付けません（カードには従来どおりの表示用の番号が出ます）。

### 保存と出力

- 「この球団を保存」で、`teams` テーブルに球団を1行、`players` テーブルに所属選手を `team_id` 付きで保存します（1つのトランザクション）。保存後はボタンが押せなくなり「保存済み（球団ID: n）」と表示されます。
- 保存した選手のカテゴリは「架空球団用」「助っ人外国人用」のままなので、「過去生成選手」やバランス確認にもそのまま出ます。
- 「CSVで保存」「Excelで保存」は保存前でも使えます。
  - CSV: 全選手を1ファイル（UTF-8 BOM）。
  - Excel: シート「概要」「投手」「野手」。
  - 列は「過去生成選手」の「全データを出力」と同じ構成に、`team_name`（球団名）を足したものです。`roster_index`（登録順）と `uniform_number`（背番号、文字列）も入ります。
  - ファイル名は `players_team_{球団名}_{日時}.csv`／`.xlsx` です。
- 「この球団を分析」で「球団分析」画面へ移り、その球団を分析できます（保存前でも使えます）。

## 球団分析

上部ナビゲーションの「球団分析」で、球団生成で作った球団を**球団単位**で分析し、実在球団（2022〜2026年版パワプロ、12球団×5年＝60チーム）の分布と比べます。生成ロジックは変えません（見る・比べる・出すだけ）。

### 使い方

1. 左のサイドバーの「分析する球団」で球団を選びます（最大12球団）。
   - 「生成中の球団（未保存）」は、球団生成画面に結果があるときだけ出ます。保存済みの球団は新しい順です。
   - 球団生成画面の「この球団を分析」から来ると、その球団が選ばれた状態になります。
2. 「実在の比較基準」で年版と、1対1で比べる実在球団（任意）を選びます。年版の**既定は2024〜2026年版（36チーム）**です（2022・2023年版はミートの基準が違うため）。2022・2023年版も選べます。
3. タブで見ます。2球団以上を選ぶと「球団比較」タブが出ます（ほかのタブは「詳しく見る球団」で選んだ1球団）。

| タブ | 内容 |
|---|---|
| 概要 | 主要指標（総合力＝査定の上位28人平均、投手力＝投手の上位13人平均、野手力＝野手の上位15人平均、全員平均、平均年齢、主力の平均年齢、外国人数、左投手数、先発・救援の厚み）と実在の百分位・判定、実在分布の中の位置、投手力×野手力、実在とずれている項目の一覧 |
| 人数構成 | 構成チェック表（百分位・判定付き）、カテゴリ別の人数と実在の中央・10〜90% |
| 能力 | カテゴリ（ポジション・投手役割・年齢帯・外国人・投打・プロ年数・入団経路・査定帯など）× 指標の表と図、実在の全選手との箱ひげ図、内部分類（選手格・型）別の能力 |
| 年齢 | 年齢別の人数（実在12球団の平均と重ねる）、年齢帯×ポジションの人数と実在平均との差、年齢帯ごとの平均査定 |
| 戦力の厚み | ポジションごとの何番手の査定と選手名（メインポジションのみ）、手薄・層が厚すぎるポジション |
| 特殊能力 | 青・赤・金・緑の1人あたり個数とランク特能点（カテゴリ別） |
| 選手一覧 | 選手の表（カテゴリで絞り込み）。行を選ぶと能力カード |
| 球団比較 | 主要指標を球団ごとに並べた表・図、投手力×野手力、カテゴリ別の比較 |

### 実在の比較基準

- 判定: 実在の最小〜最大の外＝「範囲外」（赤系）、10〜90%の外＝「やや外れ」（黄系）、それ以外＝「範囲内」。境界ちょうどは内側です。百分位は実在の中での順位（0〜100、同値は中間順位）。
- **年齢系（年齢・年齢帯・プロ年数・入団経路）の基準は、年版の選択に関わらず2026年版の12球団だけ**です（年齢が分かるのは2026年版だけのため）。
- 実在の外国人数は目安です（2022・2024・2025年版は外国人一覧と登録名で照合、2023年版と照合できなかった選手は登録名がカタカナのみ、2026年版は入団経路が「海外・その他」かつカタカナのみ）。
- ミートは2022・2023年版が約37、2024年版以降が約42で、年版の間に段差があります（ゲームの仕様変更とみられる）。そのため既定の比較基準は2024〜2026年版にしています。2022・2023年版を含めると、ミートの比較結果が変わります。
- 二刀流の選手（根尾・上原・矢澤・柴田）は、取り込み処理どおり野手として数えます。
- 選手格・型は生成だけにある分類なので、実在とは比べません。

### 出力

画面の上部の「Excelで出力」「CSV（zip）で出力」で、表示中の条件（選んだ球団・実在の年版・1対1の比較相手）の結果を出力します。未保存の球団も出力できます。ファイルは押したときに作ります。

- Excel（`球団分析_{球団名 または 複数球団}_{日時}.xlsx`）: シート「設定」「概要」「実在比較」「人数構成」「カテゴリ別能力」「年齢」「戦力の厚み」「特殊能力」「選手一覧」「実在基準」。見出し行の固定、判定の色、「概要」「人数構成」には Excel のグラフ（横棒）が入ります。グラフの元の表は最後のシート「グラフ用データ」にあります。「設定」には実在の基準（年版・チーム数）と既定の基準の注記が入ります。複数球団は1つのブックにまとめ、各シートに `team_label` 列があります。
- CSV（zip）: 上のシートを1つずつ CSV（UTF-8 BOM）にしたもの（`01_設定.csv` 〜 `10_実在基準.csv`）。
- PDF・画像・HTML での出力はありません。

### 実在データの作り直し

比較に使う実在の集計 `data/reference/real_team_stats_2022_2026.csv` はコミット済みで、アプリはこのファイルだけで動きます（起動時に HTML を解析しません）。選手単位のデータ `local_data/real_players_2022_2026.csv`（コミットしない）があると、能力タブの箱ひげ図も出ます。作り直すときは次を実行します。

```
python scripts/build_real_team_reference.py --zip-2022-2025 data/raw/powerpro_2022_2025/real_2022_2025.zip --raw-2026 data/raw/powerpro_2026_2027 --entry-route local_data/pawapuro_players_entry_route_2026.xlsx --foreign-list local_data/pawapuro_foreign_2022_2024_2025_complete_v6.xlsx
```

- HTML の取り込みは `scripts/import_real_powerpro_players.py` の関数をそのまま使います（zip は年版ごとに一時フォルダへ展開。年版は zip 内のフォルダ名で決めます）。
- 集計は `generator/team_analysis.py` の関数で作ります（生成球団の集計と同じコード）。
- `reports/real_team_reference/summary.md` に、件数、人数構成CSVとの整合チェック、外国人数の差、実在60チームの主要指標の分布が出ます。

## 選手履歴

「選手生成」画面の下部に「過去生成選手」が表示されます。ここにはSQLiteに保存済みの選手が一覧表示されます。

履歴には、生成日時、seed、投手/野手、カテゴリ、名前、年齢、国籍、地域、ポジション、選手タイプ、投打、身長、体重、能力、特殊能力、変化球、投手適正、サブポジションなどが含まれます。

## バランス確認

サイドバーの「表示する画面」で「バランス確認」を選ぶと、保存済み選手をSQLiteから読み込み、生成結果の偏りを確認できます。

確認できる主な内容:

- 投手/野手別人数
- カテゴリ別人数
- 投手/野手×カテゴリ別人数
- 年齢分布
- 野手能力平均
- 投手能力平均
- 特殊能力の出現回数
- ランク系特殊能力の分布
- 野手ポジション別人数
- 投手役割別人数
- 変化球バランス

保存済み選手がない場合は、空DBとして案内メッセージが表示されます。

## データベース

- DBファイル名: `players.sqlite3`
- 保存場所: リポジトリ直下（`app.py`と同じディレクトリ）
- 初回起動時に自動作成されます。
- アプリ更新時に不足列がある場合は自動追加されます。
- 球団生成で保存した球団は `teams` テーブルに入ります。所属選手は `players.team_id`（球団に属さない選手は0）、`roster_index`、`uniform_number`（背番号、文字列）を持ちます。
- 既存レコードを保持したままマイグレーションします。
- 生成履歴の本体なので、DBファイルを直接編集しないことを推奨します。
- `players.sqlite3`はgitignore対象であり、通常はGitへコミットしません。

## バックアップと復元

### バックアップ

個人利用では、公開作業よりDB保護を優先してください。最も簡単な方法は、アプリ停止中にDBファイルをコピーすることです。

```text
1. StreamlitをCtrl+Cで終了
2. 更新前・マスタ変更前は必ずplayers.sqlite3を別フォルダへコピー
3. 日付を付けて保存
4. DBファイルをGitへコミットしない
```

バックアップ名例:

```text
players_backup_2026-07-10.db
```

### 復元

```text
1. アプリを終了
2. 現在のplayers.sqlite3を別名で退避
3. バックアップDBをplayers.sqlite3という名前でリポジトリ直下へ戻す
4. アプリを起動
```

上書き前に必ず現在のDBを退避してください。DBは生成履歴そのものなので、削除すると同じ履歴は復元できません。`reports/`配下は再生成可能ですが、SQLite DBは生成履歴を含むため再生成できません。

## 検証スクリプト

レポート出力先の`reports/`配下はgitignore対象です。5000件規模の実行は時間と容量を使います。

### まとめて流す（`scripts/run_checks.py`）

下の検証スクリプトのうち、生成バランスの判定をするもの（`validate_team_mode.py`、`check_pitcher_control.py`、`check_age_profile.py`、`check_fictional_balance.py`、`check_foreign_balance.py`、`check_draft_balance.py`）を、同じ条件で1回で流して、結果を1枚にまとめます。個別生成のCSVは、このスクリプトが `scripts/generate_*_balance_sample.py` で作ります。

```powershell
python scripts/run_checks.py                       # 正式な規模。結果は reports/checks/summary.md
python scripts/run_checks.py --quick               # 簡易版。すべての合否が「参考」になる（reports/checks/quick/）
python scripts/run_checks.py --only validate_team_mode,check_pitcher_control
```

- 正式な規模は、各スクリプトの既定値です（球団生成の構成・背番号500球団、戦力600球団、カラー7×200球団、散らばり300球団、球団生成300球団、年齢帯は個別30000人×2＋球団500球団、個別生成は投手・野手各5000人）。時間は並列数にもよりますが15分前後です（並列のワーカーごとに数百MBのメモリを使います。足りないときは `--workers` を減らしてください）。
- `PYTHONHASHSEED=0` を固定して流します（生成結果が `PYTHONHASHSEED` によらないことは `tests/test_hash_independence.py` で確かめています。念のための固定です）。
- `reports/checks/summary.md` に、合格・要注意・受け入れ済み・不合格の件数、合格以外の項目（id・値・範囲・誤差・種類・理由）、スクリプトごとの規模と所要時間、実行したコミットを出します。各スクリプトの判定の一覧は `reports/checks/<スクリプト名>.csv`（列: id、種類、節、表示名、値、範囲、誤差、境界からの距離、合否、理由）、全部をまとめたものは `reports/checks/all_checks.csv` です。
- 終了コードは、不合格が1件でもあれば1、要注意・受け入れ済みだけなら0、スクリプトが異常終了したら2です。
- **改修の完了報告には、正式な結果（`--quick` なし）を使います。`--quick` の結果で合否を話さないでください。**

### 判定の種類・誤差・合否（`scripts/checklib.py`）

すべての判定には、次のどれかの種類が付いています。

| 種類 | 意味 | 合否の付け方 |
|---|---|---|
| 実在 | 実在データに合わせる判定 | 範囲の内側なら合格。外側でも、境界からの距離が誤差の2倍以内なら要注意、超えたら不合格 |
| 固定 | 改修前から変わっていないことを確かめる判定 | `data/config/check_baselines.json` の基準値±幅の内側なら合格 |
| 設計 | 実在とは別に決めた条件（戦力レベルの (a)(d)(e)(f)、チームカラーの目安、背番号の重複なし、「0件（仕様）」など） | 範囲の内側なら合格、外側なら不合格（誤差は見ない） |
| 参考 | 合否を付けない表示 | 表示だけ |

- **誤差**は、判定に使う値そのもののばらつきです。同じ評価関数を、生成した球団（球団単位の値）や選手（選手単位の値。年齢帯の判定は球団生成なら球団単位）を重複を許して引き直した標本で何度も（既定200回、年齢帯は100回）計算し、値の標準偏差を求めます。実在側は、実在のデータが手元にあるとき（実在の36チーム・12チーム・投手1,126人など）は同じように引き直し、実在の人数だけが分かるときは生成側の誤差を人数比で換算します。合わせた誤差は √(生成側² ＋ 実在側²) です。範囲を実在から決めていない判定（固定・設計・実在に当たらない閾値）は生成側だけです。構成の「実在の最小〜最大」は両端の値なので実在側の誤差は見ません。
- **範囲そのものは変えていません**。誤差の分を「要注意」で吸収します。表には値・範囲・誤差・境界からの距離（誤差の何倍か）・合否を並べます。
- **受け入れ済みの不合格**は `data/config/accepted_deviations.json` に記録します（`id`、`accepted_value`、`limit`、`direction`（悪い向き: upper／lower）、`reason`、`pr`、`date`）。記録された項目は、値が `accepted_value` より悪くなっていなければ「受け入れ済み」、誤差の2倍を超えて悪化したら「不合格（受け入れた値より悪化）」、範囲に戻ったら「合格」になり、記録を外すよう理由欄に出ます。記録するのは、正式な規模で流しても不合格になる項目だけです。
- **基準値**（固定の判定）は `data/config/check_baselines.json` にまとめています（値・幅・方向・最後に更新したPR・理由・日付）。意図して改修前の値を変えたときは、各スクリプトに `--update-baselines --reason "理由"` を付けて流します（`--baseline-pr "#110"` で記録するPRも付けられます）。「固定」の判定の今の値を書き込み、書き込んだ項目の前の値・新しい値を表示します。`--reason` が空なら書き込みません。
- **前回の正式な結果との比較（スナップショット）**: `run_checks.py` の正式な結果の値を、id ごとに `data/config/check_snapshot.csv`（main の結果をコミットしておく。更新の日付・理由・コミットは `check_snapshot_meta.json`）に保存しています。次に流したとき、「実在」「設計」の判定を、スナップショットからの変化で評価します（生成側の誤差だけで評価。実在側の誤差は前回と共通なので入れません）。
  - 範囲の中心（片側だけの範囲ならその境界）から**遠ざかる向きに、生成側の誤差の3倍を超えて動いた**項目は「悪化」で、**不合格として数えます**（理由欄に前回・今回の値を出します）。近づく向きの変化は「改善」と表示するだけです。誤差が0の判定（「0件」など）は、少しでも悪い向きに動いたら悪化です。
  - これは、範囲を変えずに誤差の2倍を「要注意」にしている「実在」の判定が、小さな悪化を見逃すのを補うものです（実在の36チームの誤差が大きい散らばりの判定で、散らばりが約1.3倍になっても要注意止まりになるため）。
  - まとめ（`reports/checks/summary.md`）に、「悪化」「改善」の一覧を出します。簡易版（`--quick`）では比較しません。
  - **意図した改修で値が動いたとき**は、`python scripts/run_checks.py --update-snapshot --reason "理由"` を流してスナップショットを更新します（`--reason` が空なら書き込まず、`--quick` では更新できません）。更新した項目と前後の値を表示します。更新したファイル（`check_snapshot.csv`・`check_snapshot_meta.json`）も一緒にコミットしてください。
  - 改修のPRでは、PRの説明に「スナップショットを更新した項目と理由」を載せてください。意図していない項目が動いていたら、それは悪化として見つかったものなので、更新せずに原因を直します。
  - 流れ: 改修する → `run_checks.py`（正式）→ 悪化・不合格を確認 → 意図した変化だけなら `--update-snapshot --reason` で更新 → コード・基準値・スナップショットを同じPRでコミット。
- 判定の **id** は、表示名を変えても変えません。`validate_team_mode`・`check_pitcher_control`・`check_age_profile` は英字の名前（例: `validate_team_mode.spread.投手の査定の平均.p90`）、個別生成のCSVを判定する3つは「`<スクリプト名>.<役割>.<節のキー>.<項目名>`」です。項目名を直すときは、`Result.add(..., id="元のid")` で元の id を渡してください。基準値ファイルと受け入れ記録は、この id で項目を指します。
- 各スクリプトに共通の引数: `--boot`（ブートストラップの回数。0なら誤差なし＝要注意なし）、`--quick`（すべて参考）、`--update-baselines`、`--reason`、`--baseline-pr`、`--checks-csv`。

### `scripts/validate_team_mode.py`

球団生成モードの検証です。固定seedで球団を作り、実在データと比べて `reports/team_mode/` にレポート（`summary.md` と各CSV、散布図のHTML）を出します。

```powershell
python scripts/validate_team_mode.py
```

- 既定では、構成・背番号の確認に500球団、戦力レベルの確認に600球団、チームカラーの確認にカラーごと200球団（効き具合 t=1.0・サブカラーなしに固定）を作ります。並列で数分〜十数分かかります。
- `--teams`、`--strength-teams`、`--color-teams`、`--workers` で球団数と並列数を変えられます。`--skip-color`、`--skip-strength` で一部を省けます。
- 「球団ごとの散らばり」の節では、球団生成300球団（seed 1〜300、`--spread-teams` で変更）の球団ごとの値（総合力・投手力・野手力・全員平均・投手／野手の査定の平均、先発・救援の球速／コントロール／スタミナ、野手の7能力。外国人を含み、計算は `generator/team_analysis.py`）の10%・中央・90%・標準偏差を、実在（2024〜2026年版の36チーム）と比べます。合格の目安は、査定の6指標が標準偏差の比 0.85〜1.20 で10%・90%が実在±(実在の標準偏差×0.5)、能力が標準偏差の比 1.25 以下（その能力を動かすチームカラーの球団を除いて判定。機動力→走力、守備重視→守備力・肩力、強力打線→ミート・パワー、投手王国→投手の球速・コントロール・スタミナ。メイン・サブどちらでも除き、表には除く前の値も出す）、総合力の中央が実在±2%、救援のコントロールの90%が実在＋1.0以内です。改修前・途中の段階の値と、国内選手の選手格の人数（1球団あたり）も並べて出します（`spread_metrics.csv`、`spread_class_counts.csv`）。`--spread-only` でこの節だけ（`spread_summary.md`）、`--skip-spread` で省略できます。
- 戦力レベルの判定 (e) の「強豪の中央値 > 中位の〇%点」は、総合力・全員平均が75%点、投手力・野手力が60%点です。(f) の投手指標と野手指標の相関の目安は 0.10〜0.45（実在は2026年版12球団 0.37、2024〜2026年版36球団 0.21、2022〜2026年版60球団 0.27）。
- 戦力レベルの比較には、2026年版実在12球団の選手データ（`reports/real_powerpro_players_12teams/`）を `generator/rating.py` で査定した値を使います（実在選手の変換は `generator/real_data.py`）。
- 構成確認用の球団の日本人選手で、`scripts/check_age_profile.py` の年齢帯別チェックも行います（同じ id・同じ球団なので、`run_checks.py` では `check_age_profile.py` の結果を使います）。

### `scripts/build_real_team_reference.py`

球団分析の実在比較用データを作ります（「球団分析」の「実在データの作り直し」を参照）。2022〜2025年版の zip と2026年版の zip・入団経路・外国人一覧から、`local_data/real_players_2022_2026.csv`（選手単位）と `data/reference/real_team_stats_2022_2026.csv`（球団単位の集計）、`reports/real_team_reference/summary.md` を出します。数秒で終わります。

### `scripts/check_age_profile.py`

架空球団用（日本人）の特殊能力の数（青特・赤特・緑特）、ランク特能（ランク点・B以上の数）、査定値を年齢帯別（〜21、22〜25、26〜29、30〜33、34以上）に集計し、実在（`data/reference/real_age_profile_2022_2026.csv` を平滑化した目標）と比べて判定します。
若手（〜19、20〜21、22〜23）の能力（投手: 球速・コントロール・スタミナ・変化量、野手: ミート〜捕球・弾道）の平均・標準偏差・10〜90%タイルも集計し、`若手能力の幅_改修指示.md` の目標と比べます。

```powershell
python scripts/check_age_profile.py                        # 個別生成 投手・野手 各30000人 ＋ 球団生成 500球団
python scripts/check_age_profile.py --players 1000 --teams 0   # 簡易版
```

- 若手（〜19歳）は日本人の約4%なので、年齢帯ごとに1000人以上になるよう個別生成の既定を30000人にしています。特能・ランクの判定は、基準を決めたときと同じ seed 1〜5000 で行います。
- `--save` で選手ごとの値をCSVに保存し、`--compare <保存したCSV>` で修正前と並べた表を出せます。若手の能力は、同じ選手どうしの順位相関（0.98以上）と位置ごとの差（修正前の ±30% 以内）も判定します。
- 不合格が1件でもあれば終了コード1です（要注意・受け入れ済みは0）。

### `scripts/check_fictional_balance.py`

架空球団用（日本人）の生成CSVを、実在12球団の日本人の傾向と比べて判定します。CSVは `scripts/generate_fictional_balance_sample.py` で作ります。

```powershell
python scripts/generate_fictional_balance_sample.py 投手 5000 reports/fictional_pitchers.csv 1
python scripts/check_fictional_balance.py reports/fictional_pitchers.csv
```

- 正式な判定は投手・野手それぞれ5000人（seed 1〜5000）で行います。
- 「球速の左右・役割」の節では、先発・救援×右・左の球速の平均と標準偏差、左右差、救援−先発の差、投げ手ごとの10%・中央・90%、左投手の155km/h以上の割合を、実在（2024〜2026年版の日本人投手）と比べます。
- 「コントロールの役割・左右」の節は、個別生成では下限だけを判定します（4区分の平均が実在より2.5以上低くならない、救援でコントロール60以上が9%以上）。ほかの項目（救援の幅、左右差など）は参考表示で、正式な判定は下の `scripts/check_pitcher_control.py`（球団生成）で行います。
- 「救援のスタミナ」の節は、個別生成では救援のコントロール×スタミナの相関（0.10〜0.35）だけを判定し、ほかの項目は参考表示にします（正式な判定は `scripts/check_pitcher_control.py`）。
- 不合格が1件でもあれば終了コード1です（要注意・受け入れ済みは0）。

### `scripts/check_pitcher_control.py`

架空球団用（日本人）投手のコントロールの役割・左右を、球団生成で作った球団の日本人投手で判定します（球団を生成するのでCSVは不要です）。

```powershell
python scripts/check_pitcher_control.py                # 正式: 300球団（seed 1〜300）
python scripts/check_pitcher_control.py --teams 60     # 途中確認用
```

- 先発・救援×右・左のコントロールの平均、左右差、救援−先発の差、救援の標準偏差と10%・中央・90%、救援でコントロール60以上・70以上の割合、日本人全体の平均を、実在（2024〜2026年版の日本人投手）と比べます。
- 「先発のスタミナ」の節では、先発の右・左の平均・標準偏差、左右差、先発全体の10%・中央・90%を実在（2024〜2026年版の日本人）と比べます。「総変化量」の節では、先発・救援の総変化量の平均・標準偏差、コントロール・スタミナとの相関、球団内の査定の下位⅓・上位⅓の平均を比べます（個別生成の `check_fictional_balance.py` は参考表示）。
- 「救援のスタミナ」の節では、コントロール×スタミナの相関（救援・救援の右・左・日本人投手全体）、救援のスタミナの平均（全体・右・左）・標準偏差・10%・中央・90%、スタミナ×査定の相関（救援）を、実在（2024〜2026年版の日本人の救援投手）と比べます。
- 役割の区分は、`position` が「先発」なら先発、「中継ぎ」「抑え」は救援です。
- 参考として、球団ごとの平均（救援・先発、外国人を含む。球団分析と同じ集計）の分布と、年齢帯×役割のコントロール（実在は2026年版のみ）を表示します。球団ごとの散らばりは戦力レベルによる選手格の構成で決まるため、ここでは判定に含めず、`scripts/validate_team_mode.py` の「球団ごとの散らばり」で判定します。
- コントロール20未満・球速×コントロールの相関・コントロール×スタミナの相関（+0.38〜+0.58）は、今までどおり `check_fictional_balance.py`（個別生成5000人）で判定します（コントロール×スタミナの相関は、ここでも球団生成で実在0.491±0.05を判定します）。
- 不合格が1件でもあれば終了コード1です（要注意・受け入れ済みは0）。

## トラブルシューティング

### `streamlit`が見つからない

- 仮想環境が有効か確認してください。
- 仮想環境内で次を実行してください。

```powershell
pip install -r requirements.txt
```

### モジュールが見つからない

- 作業ディレクトリがリポジトリ直下（`app.py`がある場所）か確認してください。
- 仮想環境が有効か確認してください。
- `pip install -r requirements.txt`を再実行してください。

### DBエラー

- アプリを停止してください。
- `players.sqlite3`をバックアップしてください。
- ファイル権限を確認してください。
- DBファイルやフォルダが読取専用になっていないか確認してください。

### Excel出力エラー

- `openpyxl`が入っているか確認してください。
- 出力先ファイルをExcelで開いたままにしていないか確認してください。
- 出力先フォルダの権限を確認してください。

### PowerShellで仮想環境を有効化できない

現在のPowerShellプロセスだけ実行ポリシーを一時変更します。

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.venv\Scripts\Activate.ps1
```

### ポートが使用中

別ポートを指定して起動してください。

```powershell
streamlit run app.py --server.port 8510
```

## 既知の仕様

- 金特は実在比較データに合わせて生成対象外です。
- usageは別枠情報のため生成対象外です。
- 実在選手の完全再現を目的としません。
- 同一名前が低確率で重複する可能性があります。
- ランダム生成のため少数サンプルでは分布が偏ります。
- バランス評価は5000件規模で確認する想定です。
- 助っ人外国人用は特殊能力が多めです。
- ドラフト候補用は能力・特殊能力が低めです。
- レポート類は通常gitignore対象です。

## 開発者向け情報

### 能力ランク

数値能力は1〜99に丸めたうえで、次のA〜Gランクを表示します。

| ランク | 数値 |
| --- | --- |
| A | 80以上 |
| B | 70〜79 |
| C | 60〜69 |
| D | 50〜59 |
| E | 40〜49 |
| F | 30〜39 |
| G | 29以下 |

この境界値は`app.py`の`rank()`関数の現行仕様です。

### データ保護

- アプリ停止中にDBをコピーしてください。
- アプリ更新前に必ずDBをバックアップしてください。
- マスタ変更前にも必ずDBと対象ファイルをバックアップしてください。
- SQLite DBは生成履歴を含むため再生成できません。
- `reports/`フォルダは再生成可能です。
- `players.sqlite3`などのDBファイルをGitへコミットしないでください。
- Git操作でDBを削除しないよう注意してください。
- 不要なDB削除操作をしないでください。
